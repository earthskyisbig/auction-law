# 강의 자료 — 세무에이전트 만들기

> 한 문장 요약: **세금은 변수 몇 개로 결정된다. 세무에이전트 만들기 = 그 변수 파악을 시스템으로 옮기는 것.**
> 실제 사용한 프롬프트를 그대로 싣되, 실전 사례는 개인 정보를 익명화했다.
> 최초 작성: 2026-08-16 · 개정: 2026-08-16 (변수 중심으로 재구성)

---

## 1부. 세금을 결정하는 변수 8개 — 이것부터 잡는다

세법 조문이 아무리 복잡해도, 실제 세금을 가르는 건 아래 변수들이다.
**설계의 시작은 조문 읽기가 아니라 변수 목록 만들기다.**

| # | 변수 | 뜻 | 예 |
|---|------|-----|-----|
| 1 | **시점** | 언제 샀나/팔았나/보유 중인가 | 취득일, 양도일, 과세기준일(6월 1일), 법 개정 시행일 |
| 2 | **보유기간** | 얼마나 갖고 있었나 (+거주기간) | 2년(비과세), 3년(장특공 시작), 1~2년(단기 중과) |
| 3 | **주택수** | 세대가 몇 채로 세어지나 | 입주권·분양권·오피스텔·상속·재고주택 포함 여부 |
| 4 | **금액대** | 얼마짜리인가 | 6억/9억(취득세 구간), 12억(비과세 한도), 9억/12억(종부세 공제) |
| 5 | **규제지역** | 조정대상지역인가 | 중과·거주요건·감면의 스위치 |
| 6 | **구간** | 어느 세율 구간에 걸리나 | 과세표준 구간표 |
| 7 | **누진** | 구간 넘어가면 어떻게 붙나 | 누진공제, 초과분 과세 |
| 8 | **혜택** | 깎아주는 예외에 해당하나 | 비과세 특례(일시적2주택·상속·혼인), 감면(생애최초), 공제(장특공) |

### 핵심 함정: 같은 변수인데 세목마다 "기준점"이 다르다

여기서 세금 사고의 90%가 난다. 강의에서 제일 힘줘야 할 대목.

| 변수 | 취득세 | 보유세 | 양도세 |
|------|--------|--------|--------|
| **시점** | 취득일 | 매년 6월 1일 | 양도일 |
| **규제지역 판정 시점** | 취득 당시 | — | **거주요건은 '취득 당시'**, **중과는 '양도 당시'** — 한 세목 안에서도 갈린다 |
| **주택수** | 상속주택 5년간 제외, 매매사업 재고는 포함 | 인별 합산 | 중과 판정엔 재고 **명문 포함**, 비과세 판정엔 **실질 판정** — 같은 집이 판정마다 다르게 세어진다 |
| **혜택(일시적 2주택)** | 3년 내 처분 + 이사·취업 등 사유 | — | 1년 경과 취득 + 3년 내 처분 (요건이 다르다!) |

> **실전 사례(익명화)**: 상속주택 1채를 가진 세대가 매매사업용 아파트를 추가 매입했다.
> 그 아파트 취득세 주택수를 셀 때 상속주택은 **빠졌고**(상속 5년 내), 양도세 중과 주택수에선 상속주택도 재고주택도 **들어가고**, 비과세 판정에선 재고주택이 **실질에 따라 갈렸다.** 같은 세 채인데 판정마다 세는 법이 달랐다 — 변수의 '기준점'을 세목별로 파악하는 게 왜 핵심인지 보여주는 사례.

## 2부. 변수가 곧 설계다 — 변수 → 시스템 매핑

변수 목록이 잡히면 에이전트 구조는 자동으로 따라온다. 어려운 아키텍처 얘기가 아니다:

```
변수를 채운다        →  LLM이 사용자에게 질문 (사실관계 추출)
변수의 '기준'을 확인  →  조사관이 법령 API로 원문 조회 (+ 위키 재사용)
변수 → 세율 매핑     →  세율표 JSON (수치마다 근거 조문 + 검증상태)
변수 조합 → 판정     →  파이썬 결정 트리 (특례 해당 여부)
구간·누진 → 세액     →  파이썬 계산 함수 (LLM 암산 금지)
기준이 아직 맞는지    →  독립 검증관이 인용 재확인 + 개정 시 날짜 분기 추가
```

각 줄이 시스템 구성요소 하나씩이다:

1. **질문 목록 = 변수 목록.** 실전에서 "언제까지 팔면 중과 안 되나"라는 질문에 답하기 전에 4가지(취득 시점 vs 상속 시점 / 세대 관계 / 보유·거주 / 금액대)를 먼저 물었다. 답에 따라 결론이 "기한 없음"과 "이미 늦음"으로 갈렸기 때문. **변수를 다 채우기 전에 계산하지 않는다.**
2. **세율표는 코드가 아니라 데이터.** 변수→값 매핑(6억 이하 1%, 조정 2주택 8%...)을 JSON으로 분리하고, 수치마다 근거 조문과 검증 여부를 붙인다. 법이 바뀌면 코드가 아니라 표를 고친다.
3. **판정은 if-else, 계산은 산수.** "일시적 2주택인가?"는 변수 3개(취득 간격 1년, 처분 기한 3년, 종전주택 요건)의 조합이다. LLM에게 판단시키지 말고 결정 트리로 못 박는다.
4. **시점 변수는 '날짜 분기'로.** 혼인 특례가 5년→10년으로 바뀌었으면 값을 바꾸는 게 아니라 "양도일이 2024.11.12 전이면 5년, 후면 10년" 분기를 추가한다. 과거 사안엔 과거 법이 적용되니까.
5. **검증은 남이 한다.** 만든 사람이 검사하면 안 된다 — 별도 검증관이 인용 조문·판례를 처음부터 재조회한다.

## 3부. 구축 스텝 (실제 프롬프트)

프롬프트는 짧다. **순서와 검증 질문이 핵심이다.**

**Step 0 — 조회 인프라.** 법령 원문을 가져올 수단(law.go.kr API 스킬)부터. 데이터 소스의 함정(본문검색 오작동, 판례 본문 조회 불가, IP 등록)을 실측해 기록.

**Step 1 — 에이전트 추가 + 즉시 검증.**
> `세무관련한 에이전트를 추가하고 싶어`
> (직후) `조정대상지역 재개발빌라 조합설립후 경매로 매수함. 6개월내에 매매사업자로 매도시 취득세, 양도세는 어떻게 되나`

만들자마자 변수가 잔뜩 얽힌 실전 질문을 던져 작동을 확인한다.

**Step 2 — 반복 쟁점을 위키로.**
> `경매 위키와 같은 방식으로 세법 쟁점도 위키화해줘` (요지)

취득세 중과, 주택수 산정, 1세대1주택 비과세, 일시적 2주택, 장특공... 전부 **변수의 '기준점'을 미리 조사해 두는 작업**이다.

**Step 3 — 확정 계산기.**
> `제미나이와 설계를 논의한 내용이야. 네가 다시 적정한지 검토하고, 필요시 재구성해서 만들어보자`

외부 설계안을 그대로 구현시키지 않고 **검토·재구성**을 시켰다. 아키텍처 원칙(변수→트리→계산)은 채택, 낡은 수치는 위키 검증분으로 교정, 프레임(독립 FastAPI)은 기존 하네스에 맞게 기각.

**Step 4 — 변수값 전수 검증.**
> `미검증 세율들 law-api로 검증해서 갱신해줘`

참고값 12건을 원문 조회 — 2건(생애최초 감면 구조, 혼인 특례 기간)이 실제와 달라 수정했다. **표에 '검증됨/참고값' 딱지를 붙여둔 덕에 뭘 검증할지가 자동으로 목록이 됐다.**

**Step 5 — 실전 운용.**
> (익명화) `○○구 1주택, △△구에 상속주택 1채. ○○주택을 언제까지 매도하면 양도세중과가 안되나`

흐름: 변수 질문 4개 → 조사관 병렬 조회 → 결정 트리 판정 → 검증관 게이트 → 답. 후속 정보(매매사업자, 상속 시점, 금액)가 나올 때마다 해당 변수만 다시 채워 부분 재실행.

**Step 6 — 자산화.**
> `위키등재는 세부내용은 개인정보니 등록하지 말고, 개념을 등재해줘`

실전에서 조사한 것을 일반화해 위키로. 다음 사람은 조사 없이 재검증만 하면 된다.

## Do ✅ / Don't ❌

**Do**
1. 계산 전에 **변수부터 다 채운다** (모르면 사용자에게 묻는다 — 지어내지 않는다).
2. 세율·기준값은 **데이터로 분리** + 근거 조문 + 검증상태 딱지.
3. 법 개정은 **날짜 분기 추가** (값 교체 금지).
4. 만들고 → 실전 질문 → 고치기. 검증 질문이 구체적일수록 좋다.
5. 골든 테스트 기대값은 단계별로 수기 검산 (엔진과 다르면 검산부터 의심).

**Don't**
1. LLM에게 세액 암산·특례 판정을 시키지 않는다. *(실증: 테스트 기대값을 사람이 암산해서 틀리고 엔진이 맞았던 기록이 ERRORS.md에 있다.)*
2. 변수의 기준점을 세목 간에 복사하지 않는다 (취득세의 주택수 ≠ 양도세의 주택수).
3. 외부 설계안을 무검토 구현하지 않는다 — "검토하고 재구성해라".
4. 작성자에게 자기 검증을 맡기지 않는다.
5. 오래된 판례를 연혁 확인 없이 현행에 원용하지 않는다 (그 사이 조문이 바뀌었을 수 있다).

## 자주 겪는 에러

| 증상 | 원인 → 해결 |
|---|---|
| API "사용자 정보 검증 실패" | 호출 IP 미등록 → IP 등록 또는 test 계정 |
| 판례 본문 "일치하는 판례가 없습니다" | 국세법령정보시스템 출처는 본문 미제공 → 사건명만 인용, 조세심판원 결정례로 대체 |
| 세율표가 이미지로 와서 안 읽힘 | `<img>` 태그 안에 텍스트 표가 들어 있다 → 조문 응답의 내용 키 재귀 추출 |
| 계산 결과가 기대값과 다름 | 십중팔구 수기 검산 오류 → 단계별 재검산 후 판단 |

## 수강생 재현 체크리스트

- [ ] 내 도메인의 **세금 결정 변수 목록**을 먼저 쓴다 (8개 축: 시점·보유기간·주택수·금액대·규제지역·구간·누진·혜택)
- [ ] 변수별로 **세목마다 기준점이 어떻게 다른지** 표로 정리한다
- [ ] 조회 인프라 확보 (API 검색 1건 성공)
- [ ] 에이전트 1개 + 실전 질문 1개로 검증
- [ ] 세율표 JSON 1개 세목 (수치마다 근거+검증상태) + 골든 테스트 5개
- [ ] 참고값 1개를 원문 검증해 딱지 갱신
- [ ] 실전 질문 1건을 "변수 질문 → 판정 → 검증" 흐름으로 완주
- [ ] 조사 결과 1건을 개인정보 빼고 위키로
