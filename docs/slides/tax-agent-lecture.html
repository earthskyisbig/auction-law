변수 목록이 잡히면 시스템 구조는 자동으로 따라온다. 어려운 아키텍처가 아니라 이 여섯 줄이 전부다.

3부

구축 스텝 — 실제 프롬프트

프롬프트는 짧다. 순서와 검증 질문이 핵심이다. 각 스텝을 펼쳐 실제로 입력한 문장을 확인하라.

Step 0조회 인프라 — 법령 원문을 가져올 수단부터
law.go.kr Open API 조회 스킬을 먼저 만들고, 데이터 소스의 함정(본문검색 오작동 · 국세청 출처 판례 본문 조회 불가 · OC와 호출 IP 동시 검증)을 실측해서 기록한다. 이 함정 목록이 조사관의 품질을 결정한다. 구축 프롬프트 72개는 대부분 "만들어줘" 수준의 짧은 자연어였다 (docs/PROMPTS.md 전량 수록).
Step 1에이전트 추가 + 즉시 실전 검증
세무관련한 에이전트를 추가하고 싶어
한 줄이면 된다. 중요한 건 직후에 변수가 잔뜩 얽힌 실전 질문을 던진 것:
조정대상지역 재개발빌라 조합설립후 경매로 매수함. 6개월내에 매매사업자로 매도시 취득세, 양도세는 어떻게 되나
만들고 → 바로 써보고 → 막히면 고친다.
Step 2반복 쟁점을 위키로 — 변수의 기준점 사전 조사
경매 위키와 같은 방식으로 세법 쟁점도 위키화해줘 (요지)
취득세 중과 · 주택수 산정 · 1세대1주택 비과세 · 일시적 2주택 · 장특공 등 20개 항목. 전부 변수의 기준점을 미리 조사해 두는 작업이다. 항목마다 갱신일·재검증 주기·검증상태·조사 한계를 기록한다 — 못 찾은 것의 기록이 다음 조사의 출발점이 된다.
Step 3확정 계산기 — 외부 설계안은 검토·재구성
제미나이와 설계를 논의한 내용이야. 네가 다시 적정한지 검토하고, 필요시 재구성해서 만들어보자
"구현해줘"가 아니라 "검토하고 재구성해라". 결과: 아키텍처 원칙(변수→트리→계산)은 채택, 낡은 수치는 기존 검증 자산으로 교정, 맞지 않는 프레임(독립 FastAPI)은 기각. 산출물 = 세율표 JSON + 판정 엔진 + 골든 테스트.
Step 4변수값 전수 검증
미검증 세율들 law-api로 검증해서 갱신해줘
참고값 12건을 원문 조회 — 2건(생애최초 감면 구조 · 혼인 특례 기간)이 실제 법과 달라 수정했다. '검증됨/참고값' 딱지를 붙여둔 덕에 뭘 검증할지가 자동으로 목록이 됐다.
Step 5실전 운용 — 변수 질문 → 판정 → 검증
○○구 1주택, △△구에 상속주택 1채. ○○주택을 언제까지 매도하면 양도세중과가 안되나 (익명화)
흐름: 변수 질문 4개(취득 시점·세대 관계·보유거주·금액대) → 조사관 병렬 조회 → 결정 트리 판정 → 독립 검증관 게이트(실제로 인용 오류를 잡아 정정) → 답변. 후속 정보가 나올 때마다 해당 변수만 다시 채워 부분 재실행.
Step 6자산화 — 조사 결과를 위키로 환류
위키등재는 세부내용은 개인정보니 등록하지 말고, 개념을 등재해줘
실전에서 조사한 쟁점을 개인 사안 정보 없이 일반화해 위키로. 다음 질문 땐 재조사 없이 재검증만 하면 된다 — 지식이 자산으로 쌓이는 루프.
수칙

Do & Don't

Do
  • 계산 전에 변수부터 다 채운다 — 모르면 묻는다, 지어내지 않는다
  • 세율은 데이터로 분리 + 근거 조문 + 검증 딱지
  • 법 개정은 날짜 분기 추가 — 과거 사안엔 과거 법
  • 만들고 → 실전 질문 → 고치기 루프
  • 골든 테스트 기대값은 단계별 수기 검산
Don't
  • LLM에게 세액 암산·특례 판정을 시키지 않는다 — 테스트 기대값을 사람이 암산해 틀리고 엔진이 맞았던 기록이 남아 있다
  • 변수의 기준점을 세목 간 복사하지 않는다 (취득세의 주택수 ≠ 양도세의 주택수)
  • 외부 설계안을 무검토 구현하지 않는다
  • 작성자에게 자기 검증을 맡기지 않는다
  • 옛 판례를 연혁 확인 없이 현행에 원용하지 않는다
